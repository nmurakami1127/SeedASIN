# SeedASIN 最新スコープ整理（2026-09-02時点）

3つの設計書（要件定義書・基本設計書・詳細設計書）をもとに開発を始めましたが、実際の運用状況を伺う中で、当初の想定から変わった部分・新しく分かった部分があります。この資料は「今、何を作ろうとしているか」を整理し直したものです。

---

## 1. 全体の流れ（今回の結論）

```
①【SeedASINが作る】新しいASINを探す（Amazonの検索結果ページから、ログイン不要）
②【SeedASINが作る】ASIN一覧をCSVで出力
③【人手】primary_check / accessjpの仕組みに流し込む（既存の仕組みは変更しない）
④【SeedASINが作る】結果CSV（出品可否）を読み込み、記録する
⑤【人手】セラーを見つける（今まで通り。SeedASINは自動探索しない）
⑥【SeedASINが作る】見つけたセラーを記録・蓄積する（セラー台帳）
⑦【人手・既存プログラム】統合ツールにセラーのURL/ASINを渡し、商品ASIN一覧を取得する
⑧【SeedASINが作る】統合ツールの実行IDとセラーの対応、統合ツール出力ファイル（ASIN一覧）を記録する
⑨【人手・出品ツール】実際にAmazon上へ出品する
⑩【SeedASINが作る】週次の「出品完了リスト」（ASIN+SKU）を取り込む
⑪【SeedASINが作る】⑧と⑩を突き合わせ、「どのセラー起点の商品が実際に出品されたか」を自動集計する
⑫【SeedASINが作る】直近数ヶ月で複数回・複数タイミングで出品につながっているセラーを「継続的に使えるセラー」として提案する
```

|---|---|

## 7. ASIN探索の方針（追加確定事項）

- 既存の「キーワード検索でASINを集めるプログラム」は現存するが、**出品できる確率が低く、最近は使われていない**（実績として不採用）
- 技術的には、このプログラムは`httpx`ではなく**本物のブラウザ（Playwright）＋CAPTCHA発生時は人が手動対応**という構成で動いている。**SeedASINのASIN探索も同様に「本物のブラウザ＋人の介入が時々必要」という前提で作る**（完全無人の定期バッチにはできない）
- 「既存の実績あるセラーの新着チェックだけ」に頼ると**新規セラーへの広がりが無く、同じセラーの堂々巡りになる**という課題が既知としてある
- 「確実に新しいセラーを見つけられる方法」は、現時点で御社にもSeedASIN側にも確立した正解がない
- **方針**: 複数の探索方式（既存セラーの新着チェック／ランキングページ巡回／将来的な他の方式）をStrategyパターンで差し替え可能にしておき、それぞれの方式が「最終的に出品まで至った実績」にどれだけ貢献したかを記録・比較できる仕組みにする（元の設計書のKPI-08「探索方式別成果」の考え方をそのまま活用）。**どれが正解かを決め打ちせず、小さく試しながら実績で判断する**
- 初回に試す探索方式の候補: 売れ筋・新着ランキングページの巡回（キーワード検索より的中率が高い可能性があるが未検証）

### 7.1 統合ツールによるASIN取得（追加判明事項）

統合ツールは、以下3種類の入力に対応しており、それぞれASIN・商品情報を返す:

| 入力 | 用途 |
|---|---|
| セラーページのURL | セラー起点の商品ASIN取得（既存の「セラー実績追跡」で使用） |
| カテゴリ（最大5）＋キーワード | 条件検索によるASIN探索。**ただし画面での毎回手入力が手間**なため、AIが生成したキーワードリストを自作Playwrightスクリプトで直接Amazonへ投入していた（→この自作スクリプトはCAPTCHA対応が必要な高リスクな方法） |
| ASINリスト | 指定ASINの商品情報取得（新規探索ではなく、既知ASINの情報更新用途） |

**方針決定**: 自作のAmazon直接操作スクリプトではなく、**統合ツールの画面をキーワードリストで自動操作する**方向に統一する（Amazon自体には触れず、契約している統合ツールの自動操作に閉じる）。ただし**現時点でこの自動化の優先度は低く、Phase 3の初期実装スコープには含めない**。並行して、統合ツールの提供会社へ「キーワードリストの一括アップロード機能」の要望を出す（実現すれば自動操作すら不要になる可能性がある）。

着手する際は、事前に統合ツールの利用規約（自動操作・Bot利用の可否）の確認が必要。

### 7.2 ASIN探索・自動化の要否（最終確定）

| 作業 | 今のやり方 | SeedASINで自動化する？ |
|---|---|---|
| セラー探索（新しいセラーを見つける） | 人手 | しない |
| **ブランド・ランキングページからのASIN収集（複数件まとめて）** | 人手（1件ずつ見て、ASINリストを作成し統合ツールへ投入） | **する**（複数のブランド・ランキングをまとめて処理できることに価値がある） |
| 同業セラー（禁止セラー）のASIN収集・少量（数百件程度） | 手作業＋ブラウザ拡張機能 | しない（現状で問題ない） |
| 同業セラー（禁止セラー）のASIN収集・大量（数万件程度） | 独自開発プログラムで夜間自動実行済み | 不要（既に自動化済み） |
| 統合ツールでのキーワード検索（画面操作） | 手作業 | 優先度低・後回し（7.1節） |

**結論**: Phase 3で新しく自動化するASIN探索は「ブランド・ランキングページから、複数まとめてASINを収集する仕組み」に絞る。これはAmazonの一般公開ページ（ログイン不要）を対象とするため、Seller Centralのような認証・規約リスクは無いが、機械的アクセスへのCAPTCHA対策（本物のブラウザ操作＋人の介入）は必要になる見込み（7節既述の通り）。収集したASINは、既存の統合ツールの「ASINリスト」入力にそのまま渡す想定。

**技術メモ（実装時に反映）**: Amazonはログイン不要でも、**お届け先地域（郵便番号）を設定しないと、実際に購入可能な商品・在庫状況が正しく表示されない**（未設定だと、買えない商品や違うセラーの情報が表示される可能性がある）。ブラウザ自動操作の初期化時に、以下の郵便番号を設定する処理を組み込む:
- 米国向け探索: `97005`
- 日本向け探索: `289-1223`

**対象URLの実例（実地確認・今後の参考用）**:
- ブランド商品一覧ページ（PORTER、バッグカテゴリ）
  - 日本: `https://www.amazon.co.jp/s?rh=n%3A2016926051%2Cp_4%3APORTER...`
  - 米国: `https://www.amazon.com/s?rh=n%3A7141123011%2Cp_4%3APORTER...`
- カテゴリランキングページ（`ranking_page_collector.py`実装時に使用予定、現時点では未使用）
  - 日本: `https://www.amazon.co.jp/gp/bestsellers/?ref_=nav_em_cs_bestsellers_0_1_1_2`
  - 米国（Home & Kitchen）: `https://www.amazon.com/Best-Sellers-Home-Kitchen/zgbs/home-garden/ref=zg_bs_nav_home-garden_0`

**前提知識: 価格帯分割（price splitting）とは何か、なぜブランドページには使えないか**

Amazonの検索結果は、多くの場合ページ数に上限がある（日本のAmazonでは実質30ページ程度までしか読み取れない）。対象（セラー・ブランド等）の商品数がこの上限を超えると、単純にページを最後まで辿るだけでは全件を取得できない。

これを回避するために、既存の運用（セラーページ収集）では**価格帯で検索条件を分割し、複数回に分けて検索する**という手法が使われている。これにより、1回の検索条件（例: 1000円〜1100円の範囲）内であれば商品数が絞られ、ページ数の上限内に収まりやすくなる。

**価格帯分割の具体的な実装方法（実証済み・既存スクリプトより）**:
- 米国（`amazon.com`）: `rh=p_36:{下限セント}-{上限セント}` という形式のURLパラメータ（`i=merchant-items`・`me=セラーID`・`s=popularity-rank`等と組み合わせて使用）。セラーID指定（`me=`パラメータ）と組み合わせた場合に動作確認済み
- 日本（`amazon.co.jp`）: `p_36={下限×100}-{上限×100}` という形式（`rh=`に入れず、直接のクエリパラメータとして付与）。こちらもセラーID指定と組み合わせた場合に動作確認済み

**重要な制約**: この価格帯パラメータ（`p_36`）は、**セラー検索（`me=`）と組み合わせた場合は機能するが、ブランド検索（`p_89=`）と組み合わせても機能しないことが、実際の手作業運用の中で判明している**（技術的な理由の詳細は不明。Amazon側の仕様として、ブランド検索では価格による絞り込みがそもそも受け付けられない、または無視される）。そのため、ブランドページの収集では価格帯分割ができず、**「UIに価格の絞り込み選択肢が表示されている場合だけ手動で使う」「それ以外は取れる範囲で取り、上限を超える分は諦める」**という運用が現状となっている。

**Phase 3での対応方針**: `asin_collector.collect-brand-page`では価格帯分割を実装しない（技術的にブランド検索に効かないため）。複数ページの自動巡回（1ページ目に限らず、次ページへの遷移を繰り返す）のみ実装し、ページ上限に達した分は既存の手作業運用と同様に取得を諦める。将来、ブランド検索×価格帯分割の別の実現方法が見つかった場合は、この節を更新すること。

## 9. セラー実績追跡の仕組み（最終確定）

これまでのファイル確認を踏まえ、セラーとASINの紐づけ方を最終確定する。

```
① セラー台帳（SeedASINが管理）: セラーID ⇔ 統合ツール実行ID（例: 7128337）を記録
② 統合ツールの出力ファイル（例: 7128337_....csv、日米共通フォーマット、cp932/Shift-JIS）
   → ASIN一覧が入っている。①と組み合わせて「このASINはこのセラー起点」と確定する
   → ※ セラーとの紐づけは、この時点で1回だけ確定させれば十分。以降の工程では
     セラー情報を持ち歩く必要がなく、ASINだけを追いかければよい
③ primary_checkの入力ファイル 兼 週次の出品完了リスト（listing-XXXXXという名前、実際はZIP圧縮、
   米国セラー分は21列・日本セラー分は23列で関税/州税列の有無が異なる、cp932、週1回・日米それぞれ取得）
   → セラーとの紐づけは不要（②の時点で既に確定済みのため）。ASINの中身だけを見る
   → SKU列（USNEW1751638のような番号）が付与されている行＝登録日時ベースで抽出した、出品中のASIN
④ primary_check/accessjpの判定 → 人手で橋渡し
⑤ ③のファイルそのものが週次の出品完了リストを兼ねる
   → ②で確定した「ASIN→起点セラー」の記録とASINで突き合わせ、
     「どのセラー起点の商品が実際に出品されたか」を自動集計する
```

**確定した理解**: `listing-KW02887`（米国セラー分）・`listing-AP2725`（日本セラー分）が、探していた「週次の出品完了リスト」そのもの。SKU列に番号が付与されている行が「登録日時ベースで抽出した、出品中のASIN」を表す。primary_checkへの入力ファイルと、出品完了リストは同一ファイルが兼ねている。

**11節（実際の運用フロー）を踏まえた補足**: 11.2節で判明した`primary_check.py`のOKリストは「ASINのみのテキスト」形式であり、`listing-KW02887`/`AP2725`のリッチなCSV（画像・利益・SKU等を含む）とは別物と考えられる。`listing-XXXXX`は、`primary_check.py`→アクセスジャパン→`to_accessjp.py`の出品判定チェーンとは別の、**出品後の在庫・価格・利益を監視する別ツールの出力**である可能性が高い。この理解で問題なければ、次回以降の会話で特に訂正は不要。

**技術的な注意点（実装時に反映）**:
- 統合ツールの出力ファイル・primary_check入力ファイルはいずれも**Shift-JIS（cp932）エンコーディング**。既存プログラムと同様、utf-8-sig→cp932→utf-8の順に自動判定する処理が必要
- primary_check入力ファイルは、セラーの所在国（米国／日本）によって列数・列構成が異なる（関税・州税列の有無）。取込処理はこの2パターンに対応する必要がある
- このビジネスの実態は、**日米間の価格差を利用した並行輸入・輸出（アービトラージ）**である（「日米差益」「関税」「州税」列の存在から判明）

## 11. 現状の運用フロー（日本で販売する場合、実際のヒアリング内容）

米国で販売する場合のフローは別途共有予定。以下は日本販売の実際の運用。

### 11.1 出品候補商品の探索（5つの経路）

| # | 経路 | 起点 | 手段 |
|---|---|---|---|
| (1) | 売れ筋商品のセラーページ | 自社のビジネスレポートでセッション数・カート取得率が高いASINを選ぶ→そのASINの日本Amazon商品詳細ページ→セラー一覧→セラーページURLを取得 | 人手でURL取得→統合ツールへ入力 |
| (2) | 売れ筋商品のブランド/ストア | 同様にビジネスレポートから起点ASINを選ぶ→米国Amazon商品詳細ページ→ブランド一覧 or ストアページ | Chrome拡張機能「uAutoPagerize」（無限スクロール読込）＋「ASIN」（ASIN抽出）で一覧取得→統合ツールへ入力 |
| (3) | 競合セラーの別の取扱商品 | (1)(2)で見つけたセラーの別商品ページ | 単一セラーならセラーページURL、複数セラーならブランド+拡張機能でASINリストを取得→統合ツールへ入力 |
| (4) | キーワード（統合ツール内蔵機能） | - | 統合ツール画面上でキーワード1つ＋カテゴリ最大5つを指定し直接リクエスト |
| (5) | キーワード（独自プログラム） | AIが生成したキーワード・カテゴリのリスト | 独自開発プログラム`collect_asins_from_search.py`でASINリストを取得→統合ツールへ入力 |

**重要な訂正**: 統合ツールには最初から「キーワード＋カテゴリ検索」機能が内蔵されている（(4)）。`collect_asins_from_search.py`（(5)）が別途存在するのは、この内蔵機能が「1回に1キーワードしか指定できず、AIが生成した大量のキーワードリストを一括投入できない」ためであり、統合ツール自体に検索機能が無いわけではない（7.1節の理解を補強）。

### 11.2 出品候補商品の選別（既存プログラム3本で完結、変更不要）

```
① 統合ツールの出力（商品情報）
   ↓
② 独自プログラム「primary_check.py」
   → 輸入して問題ないか判定し、OKリスト／要チェックだがOKリスト／NGリストに振り分け
   ↓
③ OKリスト（時間があれば要チェックだがOKリストも）を「アクセスジャパン」へ入力
   → 入力形式は「ASINのみのテキスト」（リッチなCSVではない）
   → 在庫・価格をチェックし、出品可能な商品リストが得られる。出品申請要否もここで判明
   → 少量ならその場で目視確認して直接出品
   → 大量の場合は結果ファイル（ZIP圧縮CSV）をダウンロード
   ↓
④（大量時のみ）独自プログラム「to_accessjp.py」
   → primary_check.pyのOKリストと、③でダウンロードしたアクセスジャパンの結果ファイルを突き合わせ
   → 売値/最安値が120%以上、または出品申請が必要なASINを除外
   → 最終的な出品可能ASINリストを出力
   ↓
⑤ ④の出力を再度アクセスジャパンへ入力し、最終目視確認の上で出品
```

**重要な訂正**: 以前見せていただいたPythonスクリプト（`primary_check`フォルダのOKリストと`from_acceessjp`のZIPを突き合わせるもの）は、**`to_accessjp.py`（④）そのもの**だった。`primary_check.py`（②、統合ツールの生の商品情報からOK/要チェック/NGを振り分けるプログラム）はまだ見せていただいていない、別の既存プログラム。

**②③④はいずれも既存プログラム・既存サービスで完結しており、SeedASINが変更・置き換えする対象ではない。** SeedASINが関わるのは11.1節（探索）のみ。

### 11.3 現状の運用フロー（米国で販売する場合）

構造は日本販売時とほぼ同じだが、以下の点が異なる。

**探索（5つの経路は同じ構成）**:
- 起点ASINは同じく自社ビジネスレポート（セッション数・カート取得率）から選ぶが、商品詳細ページは**基本的に米国Amazon**を見る
- (2)ブランド/ストア経由の探索について、日本Amazonの商品詳細ページを起点にしてもよいが、**「日米両方に出品されている商品でないと除外されるように見える」という経験則があり（未確証）、非効率なため日本ではあまりやらない**。米国販売の場合は米国Amazonを起点にすることが多い
- (3)競合セラーの別商品も同様、日本でもよいが米国で行うことが多い

**選別（プログラム名が異なる）**:

```
① 統合ツールの出力（商品情報）
   ↓
② 独自プログラム「ex_primary_check.py」（日本版はprimary_check.py、輸出版はex_primary_check.py）
   → 輸出して問題ない商品をOK／要チェックだがOK／NGに振り分け
   ↓
③ OK・要チェックだがOKリストを「USDS」（他社サービス、日本版のアクセスジャパンに相当）へ入力
   → ASINのみのテキスト形式。在庫・価格チェック、出品申請要否判明
   → 大量時は結果ファイル（ZIP圧縮CSV）をダウンロード
   ↓
④ 「to_accessjp.py」で②の出力（ex_primary_check.pyのOKリスト）と③のUSDS結果を突き合わせ
   → 売値/最安値120%以上、出品申請必要なASINを除外
   → ※ここで使う②のASINリストは、日本版と異なり「たいていは手動で作成している」
   ↓
⑤ 最終ASINリストを再度USDSへ入力、最終目視確認後、出品
```

**日本版との違いのまとめ**:
- 選別に使う既存プログラム名・外部サービス名が異なる（`primary_check.py`→`ex_primary_check.py`、アクセスジャパン→USDS）が、`to_accessjp.py`は共通で使われている（名前はaccessjp由来だが、USDS結果との突き合わせにも流用されている）
- **④の工程で使うASINリストが、日本版は自動生成に対し米国版は「たいてい手動作成」** という運用上のギャップがある。**これは選別工程内の話であり、SeedASINのスコープ外**（探索のみがSeedASINの担当という原則を維持）
